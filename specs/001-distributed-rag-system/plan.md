# Implementation Plan: Distributed RAG-Augmented LLM System

**Branch**: `001-distributed-rag-system` | **Date**: 2026-05-11 | **Spec**: [spec.md](./spec.md)

---

## Summary

Build a real distributed system that handles concurrent AI queries by routing them through an NGINX gateway to a Python master coordinator, which enriches each query with RAG context from a separate Chroma vector database and dispatches it to one of several GPU worker nodes selected by a live-data-driven load balancing strategy. Workers continuously push real-time metrics (active tasks, resource utilization, recent latency) to the coordinator, which uses those metrics to make routing decisions. The system detects worker failure via metrics staleness and automatically retries failed requests on healthy workers. The runtime is containerized and configured entirely by environment variables.

---

## Technical Context

**Language/Version**: Python 3.11  
**Primary Dependencies**: FastAPI + Uvicorn (coordinator & worker APIs), NGINX (gateway), ChromaDB + sentence-transformers (RAG vector search), httpx (async HTTP between services), Supervisord (multi-process control container)  
**Storage**: Separate persistent Chroma vector database container for RAG; Python in-memory dict (worker registry)  
**Testing**: None — out of scope per spec  
**Target Platform**: Linux containers (Docker); control container on MacBook; worker containers on cloud GPU nodes  
**Project Type**: Distributed web service (two container images)  
**Performance Goals**: Gateway must accept 1000+ concurrent inbound connections; coordinator must handle the resulting request throughput without blocking  
**Constraints**: No hardcoded values anywhere; all config via environment variables; exactly two Docker images; worker container must start independently and retry coordinator registration  
**Scale/Scope**: One control container + N worker containers (N ≥ 1); designed for 2–5 GPU nodes in practice

### Source Code (repository root)

```text
.
├── control/                        # Control container (NGINX + coordinator + RAG)
│   ├── coordinator/
│   │   ├── main.py                 # FastAPI app — /query endpoint, startup
│   │   ├── registry.py             # WorkerRegistry — live worker state
│   │   ├── balancer.py             # Three load-balancing strategies
│   │   └── rag.py                  # Chroma-backed RAG retriever
│   ├── knowledge/                  # Pre-loaded knowledge base documents (.txt/.md)
│   ├── nginx/
│   │   └── nginx.conf              # Reverse proxy: 0.0.0.0:80 → localhost:8000
│   ├── supervisord.conf            # Runs NGINX + uvicorn in one container
│   ├── Dockerfile
│   └── requirements.txt
│
├── worker/                         # Worker container (LLM inference + metrics reporter)
│   ├── main.py                     # FastAPI app — /infer endpoint, metrics push loop, registration
│   ├── Dockerfile
│   └── requirements.txt
│
├── .env.example                    # All environment variables documented with defaults
└── docker-compose.yml              # Brings up Chroma + control + one worker locally
```

**Structure Decision**: Two top-level source directories mirror the control and worker images. Chroma runs from its official image as a separate vector database service. No shared source code between control and worker — each image is fully self-contained. `docker-compose.yml` is a convenience for local development; production deploys each container independently on its target machine.

## Complexity Tracking

No constitution violations requiring justification. The notable design decisions are running two processes (NGINX + Uvicorn) inside the control container via Supervisord and running Chroma as a separate infrastructure service so RAG storage is persistent and independently inspectable.
